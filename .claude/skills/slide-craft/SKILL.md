# スライドづくりのベストプラクティス

`LESSONS.md` の個々の指摘を、題材によらず使える形にまとめ直したもの。`CLAUDE.md` の各ルールが「何をするか」なら、ここは「なぜそうするか」と「いつ・どの順で確かめるか」。末尾の括弧は、元になった教訓の ID。

## 0. 根っこにある 5 つの原則

すべてのルールは、次の 5 つのどれかから来ている。迷ったらここに戻る。

1. **1 ページ目から初めて読む人に通じるか**：「分かっている人なら通じる」は不合格。前提・主語・用語・つながりを省かない。（L019, L022, L037）
2. **聴講者の注意は 1 枚に 1 つ**：1 枚 1 メッセージ。文字は最小にし、残りは図と口頭へ。（L025, L040）
3. **事実で言い、強さを事実に合わせる**：数字・仕組み・挙動は一次情報と実物で裏付ける。裏付けより強く言わず、分からないことを飾りで書かない。（L003, L041, L042, L044, L047）
4. **見た目で伝わるものは見た目で**：画像・図・色・配置で一目で分かるようにし、そのうえで縮んだ後でも読める大きさにする。（L006, L035, L045）
5. **発表者の判断が正**：発表者が直した枚・良いと言った図は崩さない。大きく変える前に確かめる。（L012, L030, L046）

## 1. 進め方

| 段階 | やること | 確かめること |
|---|---|---|
| 構想 | トラックと各枚の一覧、持ち時間の配分を構成案として出し、了承を得る。発表者が「考え中」と言った箇所は、スライドにせず軸の候補を出して壁打ちする | 各トラックの切り口を 1 語で言えるか（L012, L026） |
| 執筆 | 1 枚ずつ見出し → `.lead` → 図 → ノートの順に書く。ノートを書きながら継ぎ目を確かめる | 見出しだけを順に読んで話が通るか（L005） |
| 描画 | `npm run images` で PNG を書き出し、必ず画像を見る。図は `npm run diagrams` で書き出して 1 つずつ見る | はみ出し・重なり・文字の大きさ・矢印の向き（L017, L045） |
| 測定 | `npm run overflow` → `npm run check` → `npm run build` | error 0（L017） |
| 指摘 | 直したら `/lesson` で記録。同じ指摘が 2 回目なら `CLAUDE.md` に格上げ | 他のデッキでも起きるか |
| 完成 | `/retro` でテンプレートに持ち帰る | — |

- 構成を変える前に `_old/slides-vN.md` に退避し、図も `_old/diagrams-vN/` に残す。
- 発表者が手で直した枚は文言を変えずに受け取り、後ろの枚とノートをそちらに合わせる。（L030）
- 発表者が良いと言った図に足すときは、段・列・向きを保って箱や行を足す。描き直しが要ると思ったら先に確かめる。（L046）
- 仕組みを説明する前に、実物（コード・設定・公式ドキュメント・実行結果）を読む。思い込みで描かない。（L041）

## 2. 構成：話の骨組み

- **最初にプロダクト・題材そのものを 1 枚で見せる**。目次の前に「何か・誰が使うか・規模」。重要度の低い話題を前提に格上げしない。（L027）
- **トラックは 1 つの切り口**（なぜ・何ができる・どう動く・どう守る・どう作る）。別の切り口の一部なら親のトラックに入れる。題は章見出しのような端的な名詞か、主語を補った問い。扉の題は目次の行と同じ文。（L004, L026）
- **抽象 → 具体**。各トラックの最初の方に全体の一枚絵を置き、細部はその一枚絵のどこの話かを示してから入る。一枚絵で決めた分類の言葉は、後の道しるべ・`.lead`・ノートでもぶらさない。（L021, L033）
- **新しい話題は、すでに出た事実から生まれる問題として導入する**（「届き続ける → 1 人では足りない → 任せる」）。後の章で定義する用語を前の章で使わない。（L037）
- **前提は先に置く**。見出しに使う用語は、その枚より前に実例つきで説明する。後の章で使う事実（データの行き先など）は、最初に出てくる枚で書いておく。（L022, L028）
- **改善の話は「後」に厚く**。改善前は 1 枚、改善後は一枚絵 → 段ごとに 1 枚 → 「課題 → どの段で防いだか」の表。（L038）
- **調べた詳細は付録へ**。END のあとに置き、扉とノートに「発表では使わない」と書く。付録も、本編と同じ情報は載せない。（L018）
- 筋に関係の薄いもの、初見の聴講者に重要でない細部は削る。全体の一枚絵は削らない。（L031）

## 3. 1 枚の設計

- 形は **見出し ＋ `.lead` 1 文 ＋ 図か画面**。見出しは短い名詞句で、その枚の働きを表す語（「困りごと」→「困りごとの解決」）。言いたいことは `.lead` で言い切る。（L025, L032）
- 左上の `.topic` で大枠の話題を示す。数枚で共有する粒度の名詞 1 語。（L023）
- 似た枚が続くときは `.navpills` と見出しで言い分ける。たくさんの中から 1 つを取り上げるときは、一覧の中の位置と「何か」を先に示す。（L009, L010）
- 並べる項目（表の行・箱・道しるべ）は同じ種類・同じ軸・同じ形にそろえる。親子があるなら親を分ける。（L008）
- 番号は 1 枚の中で 1 つの意味にだけ使う。道しるべに番号があるなら、図の項目は名前で呼ぶ。画像の番号の数と文中の「N つ」を合わせる。（L034, L048）
- 吹き出しは、指す行の直下に表の 1 行として入れる。（L016）
- 本文の文字は 18px 以上。文字が多い枚は、ノートに移すか図に描き直す。（L040）

## 4. 文章

| 観点 | ルール | 例 |
|---|---|---|
| 文体 | スライドは書き言葉、ノートは平易な話し言葉 | 置く → 保存する、AI の会社 → AI プロバイダー（L039） |
| 主語と目的語 | 明らかなとき以外は省かない。名詞を並べただけにしない | 「作る計画書」→「AI が作る書類」（L001, L019） |
| 比喩 | 何が何をするかで書く | 「受け口」→「Lambda が受け取って保存する」（L035） |
| 括弧 | スライドの文では使わない。語順か句点で本文に入れる | 「SSM（無料）」→「無料の SSM」（L029） |
| 見出し | 読点で区切らない | （L002） |
| 強さ | 裏付けの範囲で言う。調べきれない数は「以上」、他人の主張は「によると」、自分の案は「案」 | （L003） |
| 不明 | 「測定中」「未確認」だけの文は書かない。仮定を明示した試算に置き換える | （L042） |
| 語の意味 | 同じ語を別の意味で使わない | 「期限」を無料枠と削除の両方に使わない（L036） |
| 英語 | 日本語訳を主にし、元の題を小さく添える。自分の訳は発表者に確かめる | （L015） |

## 5. 数字と根拠

- 載せる数字は、聴講者の判断に関わるものだけ。正確な細部は付録へ。（L031）
- 出典は `.link` で載せる。料金・仕様は公式の価格表・ドキュメントから取り、時点を書く。（L041, L044）
- **見積もりは前提を全部出す**：構成のすべての部品について、無料枠の有無と、時間とともに積み上がる量を洗い出す。仮定は図に明示する。（L044）
- **実測していない値に頼らない**：実行時間やデータ量は平均を仮定せず、設定の上限（Timeout など）で計算して「最大で〜」と書く。上限で予算を超えるなら、そのときに何が起きるかも書く。（L047）
- **前後の枚を照らす**：数字を載せた枚を足したら、前後の枚の上限・件数・単価と矛盾しないか確かめる。（L044）
- デッキ自身の数字（枚数・時間・指示の回数）は、仕上げの前に数え直す。（L020）

## 6. 技術の仕組みを見せる

構成図で「何がある」を見せて終わらない。主要な部品について、次の順に見せる。（L041）

1. **1 回の処理で何が起きるか**：入力と出力の実物、処理の順序（コードの順序と一致させる）。
2. **前提の仕組み**：実行環境・課金のように、知らないと誤解する仕組み。聴講者が次に抱く疑問（どのくらい・設定できるか・既定値）への公式の答えを添える。
3. **根拠**：実際のコードや設定の抜粋（デフォルメ可、説明用と明記）と公式ドキュメントのリンク。
4. **AI の処理**：出力だけでなく、入力の全部（指示の文・利用者の入力・渡すデータ）と、渡していないもの。実際に動かした記録を、日付とモデル名つきで。
5. **AI の仕組み（エージェントなど）**：実際のファイル名と中身の抜粋で見せる。

## 7. 図と画像

- **画像を先に考える**。Web の操作は実画面を撮り、番号つきの枠と吹き出しを付けて 1 枚を大きく。そこへのたどり着き方（どのタブ・ボタン）も見せる。押したボタンは枠で強調する。（L006, L007）
- 紹介するサイトは最初の紹介の枚で埋め込み、背景に同じ画面のキャプチャを置く。画面が変わったら撮り直す。（L013, L024）
- **縮んだ後の大きさで考える**：図の文字は、表示幅で縮んだ後で補足も 14px 以上。収まらなければ文字を小さくせず情報を減らす。（L045）
- **線はまっすぐ**：つなぐ箱の中心をそろえ、矢印を水平・垂直に。斜め線と不要な折れ曲がりを残さない。（L035）
- **記号は等幅の書体で**：見出し用の太い書体では = × ÷ が潰れる。（L043）
- **誰がするかを描き分ける**：人・ブラウザ・プログラム・AI・クラウドが自動で、を段や枠で分ける。運用の手順は「誰が何をするか」の流れ図にする。（L036, L041）
- **強調と文を一致させる**：色を付けた部分・薄くした部分・矢印の向きが、その枚の文と合っているか。（L036）
- **前後の比較は同じ枠組みで**：同じ配置で描き、差分だけを強調し、凡例を付ける。（CLAUDE.md「前と後を比べるとき」）
- 扉のイラストは、内容に合った人や場面を描く。（L014）

## 8. 発表者ノートと記事への転用

- ノートは、そのまま読める平易な話し言葉の原稿。1 枚ごとに秒数を書き、最後に次の枚へのつなぎを入れる。持ち時間の配分は目次のノートに。（L005）
- 用語は口頭で短く言い換える（「Issue、つまり課題を管理するチケット」）。スライドから移した補足は、ノートに残っているかを確かめる。（L040）
- 演出の指示（「ここで画面を操作」）は、括弧で 1 行に分けて書く。記事に転用するときに機械で落とせる。
- 記事にする前に、初見の読者役のサブエージェントに画像と本文を 1 枚ずつ照らして読ませ、初出の用語・突然出る事実・前後の矛盾・本文が触れない画像の要素を洗い出させる。裏を取ってからノートの側を直す。（L037）
- 記事にするときは「スライド 1 枚 ＋ その枚のノート」を並べる（`npm run article`）。演出の指示・秒数・付録の断り書きは落とし、スライドのリンクは各枚の下に「参考」として残す。

## 9. 仕上げの点検リスト

仕上げの前に、全枚を通して確かめる。点検はサブエージェントにソースと照らさせ、裏を取ってから直すと漏れが少ない。（L036）

- [ ] 見出しだけを順に読んで、話が 1 本の筋で通るか
- [ ] 各ノートの最後に、次の枚へのつなぎがあるか。合計時間が持ち時間に合うか
- [ ] 誰がするのか（人・プログラム・AI・クラウド）が、図と文で取り違えようがないか
- [ ] 同じ語を別の意味で使っていないか。比喩・括弧・話し言葉が残っていないか
- [ ] 「だけ」「必ず」「止まる」「無料」などの言い切りが、実装や事実より強くないか
- [ ] 数字の前提が前後の枚と矛盾しないか。見積もりは上限で計算しているか
- [ ] 図の文字が縮んだ後でも読めるか。番号の数と文の数が合っているか。番号が 2 つの意味で使われていないか
- [ ] 図の強調・矢印の向きが文と合っているか
- [ ] デッキ自身の数字を数え直したか
- [ ] `npm run overflow`・`npm run check` が error 0 か

## 10. このスキルを育てる

- 新しい指摘は `/lesson` で `LESSONS.md` に足す。既存の原則で説明できるなら、この表の該当する節に 1 行足し、教訓の ID を添える。
- どの原則でも説明できない指摘が出たら、0 章に原則を足すかを `/retro` で検討する。
